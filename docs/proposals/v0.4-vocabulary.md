# Proposal: one vocabulary for eipagent (v0.4.0)

Status: **implemented in v0.4.0.** Decisions: `model_`, `threads_`, `hook_`, and `sdk.Plugin` (the compiled-plugin struct keeps its name `eipagent.Plugin`, and the facade alias for `sdk.Plugin` is `eipagent.PluginAPI`).

## Why

The catalogue lists about 45 plugins across 9 areas, under names borrowed from three projects. The top-level API comes from the AI SDK, middleware and memory from LangChain, and the plugin API from DeepSeek Harness (Cordis). The model underneath is small, but users meet three dialects and a long list of names, so it looks like many concepts.

The goals are:

1. **One concept to learn.** A plugin is one `Apply` function that can add tools, hooks and services. Everything else is a consequence.
2. **Go words.** No `ctx *sdk.Context` next to `ctx context.Context`. Plain names instead of borrowed jargon.
3. **Users rarely type plugin names.** Common setups are options, and plumbing loads itself.
4. **One documentation section** that says, for each kind of plugin, when to use it, which built-ins exist and how to write your own.
5. **No breakage.** Every old name keeps working, with a one-time deprecation log, until v1.0.

## 1. The concept, stated once

A plugin is a Go file (or a compiled `eipagent.Plugin`) with `func Apply(p *sdk.Plugin) error`. Inside `Apply` it calls whatever it needs:

| You want… | Call | Example |
|---|---|---|
| the model to be able to do something | `p.AddTool` | look up an order, run a query |
| something to happen around every model or tool call | `p.WrapModel`, `p.WrapTool`, `p.OnRunStart`, `p.OnRunEnd` | retry, approval, PII masking, logging |
| other plugins to use something you provide | `p.Provide` | a model provider, a database, a sandbox |
| work in the background, stopped on unload | `p.Effect` | a timer, a webhook listener |

A plugin is not of one "kind". The same plugin may call all four. The kinds below describe what each built-in plugin does, to help people find things. Plugin authors never have to pick one.

## 2. Go-flavoured API renames

All old names stay as deprecated aliases (type aliases or thin wrappers) until v1.0.

| Today | Proposed | Why |
|---|---|---|
| `sdk.Context` / `eipagent.PluginContext` | `sdk.Plugin` / `eipagent.PluginAPI` | `ctx` means `context.Context` in Go. Plugin code currently has both, named `ctx` and `c`. |
| `func Apply(ctx *sdk.Context) error` | `func Apply(p *sdk.Plugin) error` | Reads naturally: `p.AddTool(...)`. |
| `var Inject = []string{...}` | `var Requires = []string{...}` | Says what it means. `?x` (optional) and `x/*` (any) stay. |
| `OnAgentStart` / `OnAgentEnd` | `OnRunStart` / `OnRunEnd` | They fire per run (`Generate`, `Stream`, `Resume`), not per agent. |
| `OnStepPrepare` | `BeforeStep` | Plain. |
| `OnModelAfter` | `AfterModel` | Plain, and matches `WrapModel`. |
| `OnDispose` | `OnUnload` | That's when it runs. |
| `WrapModel`, `WrapTool`, `Provide`, `Service`, `AddTool`, `Effect` | unchanged | Already clear. |
| `Generate`, `Stream`, `GenerateObject[T]`, `Thread`, `Tool`, `With…` options | unchanged | Idiomatic, and familiar from the AI SDK. |

Plugin-facing types stay structs of functions (`sdk.Provider{Generate: …}`), not interfaces. Interpreted plugins can't implement compiled interfaces. The docs will say so in one sentence, so Go developers don't wonder why.

## 3. Names that say what a plugin does

Built-in plugins get a prefix by what they do. This is a naming convention for the plugins we ship, never a rule for anyone else's.

| Kind (prefix) | What it does | Today → proposed |
|---|---|---|
| **`model_`** | Connects a model provider (`model/<name>` service) | `llm_openai` → `model_openai`, `llm_anthropic` → `model_anthropic`, `llm_gemini` → `model_gemini`, `llm_mock` → `model_mock` |
| **`tool_`** | Adds tools the model can call | `tool_shell`, `tool_fs`, `tool_time` (unchanged); `tool_http_fetch` → `tool_fetch`; `memory_store` → `tool_memory`; `agents` → `tool_subagents`; `skills_dir` → `tool_skills`; `mcp_client` → `tool_mcp`; `tool_sandbox` (unchanged) |
| **`hook_`** | Runs around model or tool calls | `mw_retry` → `hook_retry`, `mw_fallback` → `hook_fallback`, `mw_limits` → `hook_limits`, `mw_summarize` → `hook_summarize`, `mw_hitl` → `hook_approval`, `mw_auto_review` → `hook_review`, `mw_pii` → `hook_pii`, `mw_tool_errors` → `hook_tool_errors`, `mw_logger` → `hook_log`; `hook_guard`, `hook_stats` (unchanged) |
| **`threads_`** | Saves conversations and paused approvals (`threads` service, was `checkpointer`) | `checkpoint_inmem` → `threads_inmem`, `checkpoint_file` → `threads_file`, `checkpoint_sql` → `threads_sql` |
| **`memory_`** | Long-term memory the agent reads and writes (`memory` service, was `store`) | `store_inmem` → `memory_inmem`, `store_file` → `memory_file`, `store_sql` → `memory_sql` |
| **`sandbox_`** | Creates isolated places to run code (`sandbox/<name>`) | `sandbox_local`, `sandbox_docker` (unchanged) |
| **`workspace_`** | Where shell and file tools act (`workspace` service, was `exec`) | `exec_local` → `workspace_local`, `exec_sandbox` → `workspace_sandbox` |
| **`trigger_`** | Starts runs without a person typing | `trigger_webhook` (unchanged); `jobs` → `trigger_schedule` |
| **`trace_`** / **`audit_`** | Telemetry and evidence | `trace_file`, `trace_otlp`, `audit_http` (unchanged); `audit_jsonl` → `audit_file` |
| **`secrets_`** | Resolves `secret://NAME` | `secrets_env`, `secrets_vault` (unchanged) |
| *(no prefix)* | Core pieces | `policy`; `loop` (was `loop_default`); `db_sql` |

Old plugin names and old service names (`llm/…`, `checkpointer`, `store`, `exec`) resolve to the new ones and log a deprecation once.

## 4. Plumbing that loads itself

Users shouldn't have to know about plugins they never chose:

- **`loop`** is always loaded unless something else provides `loop`.
- **`db_sql`** loads when a `*_sql` plugin needs `db` and a DSN is configured.
- **`workspace_local`** loads when `tool_shell` or `tool_fs` needs `workspace` and none exists.
- **`threads_inmem`** loads when `Thread()` is used and no `threads` provider is configured.

Each automatic load appears in `eip config dump` and `agent.Status()` as "auto", so nothing is hidden.

## 5. Options for common setups

Most apps should never need a plugin name:

```go
agent, _ := eipagent.New(
	eipagent.WithModel("anthropic:claude-sonnet-5-5"),
	eipagent.WithPersistence("postgres", "secret://DATABASE_URL"), // threads_sql + memory_sql + db_sql
	eipagent.WithApprovals("send_email", "issue_refund"),         // hook_approval
	eipagent.WithSandbox("docker"),                               // sandbox_docker + workspace_sandbox
	eipagent.WithAudit("/var/log/eipagent/audit.jsonl"),          // audit_file
	eipagent.WithTracing("http://otel-collector:4318"),           // trace_otlp
	eipagent.WithMCP("github", "npx", "-y", "@modelcontextprotocol/server-github"),
)
```

Each option is a thin layer over `WithPlugin`. Its doc comment names the plugins it loads, so moving down a level is one step.

## 6. Writing a plugin starts from a goal

`eip plugin init weather` asks what the plugin should do, in the user's words:

```text
What should weather do?
  1. Give the model a new ability            (adds a tool)
  2. Watch or change model / tool calls      (adds a hook)
  3. Connect a model provider                (provides model/weather)
  4. Remember things / save conversations    (provides memory or threads)
  5. Run code somewhere isolated             (provides sandbox/weather)
  6. Start runs from outside (webhook, timer)
```

`-template` still works for scripts. `eip plugin inspect` and `validate` end with a plain summary of what the code does, so nobody has to classify a plugin first:

```text
weather: adds 1 tool (weather) · wraps tool calls · needs: secrets (optional) · permissions: net
```

## 7. Documentation: everything under one "Plugins" section

The docs site and PLUGINS.md get one section, in this order:

1. **Plugins in five minutes.** The concept from section 1, the four calls, and "options first, plugins when you need them".
2. **What to use when.** One goal-first table: *I want to…* → option or plugin → page. For example: "keep conversations across restarts → `WithPersistence` / `threads_sql`", "ask a person before a tool runs → `WithApprovals` / `hook_approval`".
3. **One page per kind**, each with the same five parts:
   - **What it is**, in one paragraph and one diagram line (where it sits in a run);
   - **When to use it, and when not to** (for example, a hook rather than a tool when the model shouldn't decide);
   - **Built-ins**: each plugin's config keys with defaults and a minimal working snippet;
   - **Write your own**: the `eip plugin init` choice, a complete working file, the test that proves it, and how to load it;
   - **Gotchas**: permissions it needs, ordering and priority, Yaegi limits.

   The kinds: Tools · Hooks · Model providers · Threads & memory · Sandboxes & workspaces · Triggers · Telemetry & audit · Secrets · Policy.
4. **Shipping plugins**: manifest, validate, sign, install, approve, update, roll back (exists today).
5. **Permissions and security for plugin authors**: what each permission unlocks, and what's never available.
6. **Reference**: the `sdk.Plugin` API, generated from doc comments so it can't drift.

The current pages (Everything is a plugin, Writing a plugin, Plugins at runtime, Shipping plugins, Middleware, Standard plugins) fold into this section.

## 8. Compatibility and release

- **v0.4.0** (minor): everything above, with aliases for every old name: plugin names, service names, `sdk.Context`, `Inject`, the hook methods. Each old name logs a deprecation once per process.
- **Gbot** (and anyone on v0.3.x) keeps working without code changes. It would only see deprecation logs for `llm_mock`, `checkpoint_sql`, `store_sql` and `memory_store` until it renames them.
- **v1.0** removes the aliases, after at least one minor release with them.
- The CHANGELOG lists every rename in an old → new table. `eip plugin validate` warns when a plugin uses an old name, and offers `eip plugin fix` to rewrite them.

## Open questions for you

1. **`model_` vs keeping `llm_`.** `model_` matches `WithModel` and the `model/<name>` service. `llm_` is the common term elsewhere.
2. **`threads_` vs `conversations_`.** `Thread()` is already the facade's word, so I lean to `threads_`.
3. **`hook_` vs keeping `mw_` (middleware).** "Hook" matches the SDK calls (`WrapModel` is a hook). "Middleware" is the LangChain word.
4. **`sdk.Plugin` vs another name** for what `Apply` receives, for example `sdk.Host` or `sdk.Scope`. `Plugin` reads best (`p.AddTool`), but it also names the compiled-plugin struct `eipagent.Plugin`, which would become `eipagent.Compiled` or similar.
